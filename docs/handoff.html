Before you push

The repo is public. Nothing secret may ever be committed — run a secret scan before every push. Every credential is a Render env var or a chmod 600 file under ~/.anthropic/.

README.md at the repo root is the reference manual — 1,400 lines, every mechanism explained. This page is the map to it, and mirrors docs/HANDOFF.md, docs/RUNBOOK.md and docs/DECISIONS.md in the repo.

Three truths to understand before changing anything

The join is on names, not ids

Branch exposes ~ad_name and ~ad_set_name but no ids, so ad name is the only shared key with Meta. For Google, Branch leaves the ad name empty but fills in campaign and ad group — which is why a Google CPT exists at all, and why it stops at ad-group level. A campaign renamed mid-window shows as two rows until the window rolls past the rename.

Pro rata is the only reading

Branch trials carrying no ad name are allocated to Meta and Google in proportion to each platform's share of attributed volume. Google's own measured trials are never in the pool being divided — putting them back makes the calculation circular, which was the original bug. meta_pro + google_pro == branch_total, exactly. There is no switch; the numbers are always pro rata.

Two CPTs on Google, never averaged

One spend, two counts of the same event. Branch attributes a trial from the install it saw; Google Ads attributes it from the click it served, over its own lookback. They disagree by 2% on Speakeasy, 15% on Funda and 72% on Postly. Averaging them would invent a third number that is nobody's measurement, so both are shown and only the Branch one is judged against the target — that is the definition the target was agreed against, and the one every Meta tab and the Blended view already count.

A missing value is not a zero

"We do not know what this cost" and "this cost nothing" are opposite claims. A stored day lacking an impressions key means not recorded; trials Branch refused to answer means unknown. Every one renders as a dash. Two live bugs came from collapsing that — the worse reported a blended CPT of ₹354 against a true ₹191, because a guard added on Google's side was not added to the identical hole on Meta's.

Not a data bug

macOS gotcha, worth remembering beyond this project

A process launched as a dev server — and likely launchd and cron too — is not granted access to ~/Desktop, so an import from a Desktop path raises ModuleNotFoundError at serve time even though the identical import works from a shell. Nothing long-running may depend on a path under ~/Desktop, ~/Documents or ~/Downloads.

Access

There is no login, by the owner's explicit decision after being told a public .onrender.com URL exposes live spend, budgets and every ad name. Mitigations shipped instead: X-Robots-Tag: noindex, a disallow-all robots.txt, and per-brand links.

Per-brand links narrow "anyone with the URL" from one secret covering everything to one secret per team — /b/<value>. Opening one locks the page to that brand and hides the brand switcher; every API call carries k= and the server narrows the request. A valid key asking for another brand is served its own brand; an invalid key gets a 403 naming no brands and revealing no count.

Say it correctly

The link is not a login. A forwarded link works until rotated, and rotating is changing one env var — no deploy. ROOT_OPEN is currently 1, so the bare / URL still serves all brands with full controls; set it to 0 the day every team holds its own link.

A full capability gates the two things that make the app spend: a forced Meta roster re-read and a longevity recompute. Team links are read-only in that sense; BRAND_LINK_ALL is not. Ops endpoints ignore links entirely and require the bearer token.

Caching — three layers, and why

Meta and Branch are the constraint. Everything here exists to reduce calls to them.

  • In-process payload cache, CACHE_TTL=780s, stale-while-revalidate. A woken instance answers instantly from its last numbers and refreshes behind the request. One gunicorn worker on purpose — a second keeps its own copy, doubling upstream calls while halving the hit rate.
  • GCS-persisted artifacts — settled days, and the payload cache itself, so a cold instance serves in ~0.5s instead of a 10–17s rebuild on top of a 15–30s wake.
  • Browser IndexedDB, soft 90s / TTL 15 min / hard 12 h, keyed on APP_VERSION. A warm reload renders the page in 13 ms and 4,136 matrix rows in 80 ms with zero network.

The page refreshes every 15 minutes, unforced — the first tab past the server TTL triggers one rebuild and everyone else is served from it. Hidden tabs skip the pull. A /healthz ping every 10 minutes keeps the instance warm and touches no upstream API.

Version stamps

PRORATA_MODEL, SERIES_SHAPE, row_cap, APP_VERSION. Change the shape of a stored thing and bump its stamp — otherwise old artifacts are served against new code, which has already happened twice.

Counter-intuitive: a 3-day window sits entirely inside the settle window, so it is 100% live and is the slowest view. 30- and 90-day windows are mostly stored, and faster.

Deploy

Deploys run from GitHub Actions

Render reports autoDeploy: yes and autoDeployTrigger: commit, and both are correct — but the repo has no webhook and no Render GitHub App installation, so GitHub never told Render a push happened. All 40 deploys before 27 Aug 2026 were trigger: api, and the sibling postly-insta-daily is the same: not a regression, just a connection that was never established. Toggling autoDeploy and re-PATCHing repo return 200 and change nothing; reconnecting needs the dashboard's OAuth flow.

So .github/workflows/deploy.yml does the missing webhook's job: on a push to main it calls Render's deploy API, waits, and fails the run unless /healthz comes back naming the pushed commit — during a roll the old instance still answers, so a plain 200 cannot tell a finished deploy from one that never started. Docs-only pushes deliberately skip the deploy; the Actions tab's Run workflow button ships one anyway. The RENDER_API_KEY repo secret is the credential: rotating the Render key means updating that secret in the same breath.

The Render trap that cost 20 minutes once

Render logs ==> Your service is live 🎉 and the API reports live before it has detected the open port. Until the ==> Detected service running on port NNNN line appears — five minutes later, on one deploy — every request returns a bodiless text/plain 404, not a 502 and not a wake screen. Tell them apart by the rndr-id response header: present means the request reached the app, absent means it died at Render's edge. Don't debug the app during that window.

Env vars change with no deploy — but Render env overrides code defaults, and one of them (CACHE_TTL=90) silently defeated a code change once. Check there before concluding a change didn't ship.

Verifying a UI change

Do not grep a DOM dump for an error string

This template's source contains the words ReferenceError, loading and every class name you might search for — so a grep matches on a healthy page and a broken one alike. That mistake shipped a live ReferenceError that broke the Google and Blended views, twice. Drive a real browser and read Runtime.exceptionThrown over CDP instead. Count rendered elements by class, not by substring.

Playbooks

The page shows a dash where a number should be

Working as designed, in almost every case. A dash means unknown, never zero. Check which: Branch refused (rate limit), the day predates the field being stored, or the credential is down. /api/google/status answers the Google half directly.

Google figures vanish

python3 tools/google_ads_check.py

Four things must be true and they fail in ways that look identical from outside — an empty result can mean no spend, test access only, wrong account or token expired. The check tests them in order and stops at the first failure.

  • invalid_grant → the refresh token died. Publish the consent screen, run tools/google_ads_token.py, update the Render env var.
  • PERMISSION_DENIED on every account → login_customer_id is wrong. It names the manager you act through, never the account you are reading. The correct value is the Testbook MCC 3343252288. This looks exactly like a test-level developer token and was misdiagnosed as one for an hour.
  • Everything passes but spend is empty → genuinely test-level developer access.

listAccessibleCustomers returns what the user reaches — one manager — not the accounts beneath it. Expanding to the real 18 needs customer_client.

Meta calls start failing

Codes 4, 17 and 613 are rate limits, and they bind on request time, not request count. The app degrades rather than erroring: budgets and statuses go unknown while spend and trials keep working. Speakeasy's accounts run hot from its own automation, so expect degraded reads there more often. Nothing to do but wait, unless it is persistent — the fix is Meta Standard Access, not more retries.

Branch starts returning 429

Branch throttles per app key and caps a page at 1,000 rows. A backfill once exhausted the quota and took the dashboard's own numbers down with it. Run backfills overnight, with a budget, never during the day.

The instance is asleep

Expected on the free plan: ~15 min idle → spin-down, 15–30 s cold wake. The app answers a woken request from its last cached numbers and refreshes behind it, so the wake shows real figures rather than a blank page.

Do not add a 24/7 keep-alive pinger

Render's free tier is 750 instance-hours per month per workspace, and this workspace runs three free web services. Keeping one awake round the clock is 744 h, which exhausts the pool — and Render's response is to suspend every free web service in the workspace until the 1st. A windowed keep-alive was offered and declined on 23 Aug 2026. The real fix, if it comes up again, is Starter at $7/mo.

A stored day looks wrong

Nothing rechecks a stored day, so a day stored while still moving stays wrong forever — HISTORY_SETTLE_DAYS=3 exists for exactly this. A day where both sources return nothing is refused and never written, because "no spend" and "past retention" are indistinguishable. To re-store a range, use tools/backfill_history.py — resumable, skips stored days, refuses unsettled ones.

Numbers don't match the code you just shipped

Cache layering, in order of likelihood: the browser's IndexedDB copy (bump APP_VERSION), the server payload cache (wait out CACHE_TTL, or ?force=1), a stored artifact whose shape changed (bump its stamp), or a Render env var overriding the code default.

Routine tasks

  • Add a brand — one entry in BRANDS, one Branch key pair, one BRAND_LINK_*. No other file changes.
  • Change a CPT target — cpt_target in BRANDS. None means show the number, do not colour it.
  • Rotate a brand link — change the Render env var. No deploy.
  • Check a backfill before deleting its jobs — /api/backfill/google?brand=X&budget=10&dry=1; pending_after: 0 across all brands means done.
The CSS trap

The semantic .good / .warn / .bad rules must stay at the very bottom of the <style> block with their .kpi .v.x, td.x and tfoot td.x variants. .kpi .v, td and tfoot td each declare a colour and out-specify a bare .bad, which silently turned the CPT colour coding off with no error — it just rendered navy. Verify by reading the computed colour, not by eyeballing.

Document three

The decisions

docs/DECISIONS.md

Things that look like bugs, omissions or easy wins, and are none of those. Each was decided deliberately, most after getting it wrong the other way first. Reverse any of them if there is a reason — but know what you are reversing.

No login

The owner was told plainly that a public URL exposes live spend, budgets and every ad name for seven accounts, and chose no login anyway. Do not re-litigate this unprompted. ADMIN_PASS switches HTTP basic auth on with no code change — path already tested. Offer it if the exposure becomes a real problem; not otherwise.

Pro rata is the only mode, and there is no badge

There was a measured/pro-rata switch. The owner removed it — the measured reading was the useless one — and then removed the badge announcing it. The numbers are always pro rata and the page does not say so; the explanation lives in the info panel.

An unagreed CPT target is worse than none

cpt_target: None renders the figure uncoloured. A red cell reads as an instruction, and borrowing another brand's target to have something to colour against is how you get someone acting on a number nobody agreed to.

Testing and trial spend are never blended

A testing campaign is looking for a creative that works and is expected to cost more per trial; a trial campaign is scaling one that already does. Blending them produces a CPT that describes neither, and judging a testing ad set against the trial target kills the pipeline that feeds it.

The 15-minute refresh is unforced

The old 30-minute cycle used force, bypassing the server cache — so every open tab paid for its own rebuild. Unforced at 15 minutes makes fewer upstream calls than forced at 30. The /healthz keepalive does not skip hidden tabs, because keeping the instance warm is the one thing worth doing while nobody is watching.

A closed day is not a settled day

Storing unsettled days provisionally would make 3-day windows fast — they are currently the slowest view — but it would change what yesterday's spend means. Deliberately not done.

Ad sets renames itself to Ad groups on Google

Same slot, one rung below campaign. Two buttons meaning the same thing on different channels is worse than one that renames itself. Tabs that mean nothing on a channel are hidden, not greyed.

Hook rate divides by video impressions, not all impressions

Video was added to the pull a day after impressions, so days settled in between hold impressions and no video. Both video rates divide by vimp — the impressions of rows that actually reported video — and a day without video is blank, never a zero hook rate; on the trend it draws as a gap. The 3-second count has no field of its own in v21, so it comes from the video_view entry inside actions, narrowed with filtering — a filter checked against an unfiltered pull first, because if it dropped rows it would have deleted spend, not just video.

The Google creative count is assets, not ads

A Google ad group has exactly one ad — App campaigns put the variety in the assets — so counting ad_group_ad returns 1 on every row and answers nothing. The Creatives column counts serving video and image assets, with retired ones counted separately: a group holding 98 live and 488 retired creatives is not running 586. It is also the only column there that is current state rather than the selected window, since assets carry no date on that resource.

Google's Conversions column, never All conversions

The same event usually arrives in Google twice — once from Branch, once from Firebase — and only one feed is marked primary. all_conversions counts both and reports a CPT well below the truth. The match from Branch event to Google conversion action is on the name, after stripping the timestamp Google appends to a re-imported event; two of the three brands are named that way, so an exact-suffix test finds nothing and reads on the page as "Google reported no conversions".

Blended stops where the two are comparable

A Meta ad set and a Google ad group are not rows of the same table. Blended is the only view where the channels are added, and it has no per-row breakdown for that reason.

No build step

3,839 lines of hand-written HTML is a lot for one file. It keeps the whole UI editable by anyone who can read HTML and makes a deploy a git push. Still the right trade here.

Every third source is optional

Meta is the one hard requirement — it is the only source of spend, and spend is what every other number divides by. Branch missing degrades a brand to Meta-only, a legible state. Google, Classplus and the history store are each never load-bearing: with no credential or the service down, they return empty, say why, and the page renders as it did before they existed.

The link is not a login

Per-brand links narrow one secret covering everything to one secret per team. A forwarded link keeps working until rotated. Say "access link", never "login".
